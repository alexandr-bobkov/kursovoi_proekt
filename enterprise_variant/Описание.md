# Курсовой проект: Развертывание отказоустойчивой Enterprise-инфраструктуры в Yandex Cloud

## Введение и цели проекта
Данный проект представляет собой полностью автоматизированную систему для развертывания безопасной, масштабируемой и отказоустойчивой веб-инфраструктуры в облаке Yandex Cloud.

**Главная особенность проекта:** Реализован подход **"One-Click Deployment"** (Развертывание в один клик). Весь процесс, от создания виртуальных машин и настройки сети до установки баз данных, настройки сайтов и дашбордов мониторинга, выполняется автоматически с помощью связки Terraform и Ansible без ручного вмешательства администратора[cite: 8].

## 0. Доступ к компонентам системы (Результат работы)

После того как автоматика завершает работу, инфраструктура доступна по следующим адресам (IP-адреса выдаются динамически и выводятся в консоль благодаря файлу `outputs.tf`[cite: 4, 6]):

### 🌐 1. Веб-приложение (Пользовательский трафик)
*   **Адрес:** `https://<публичный_IP_балансировщика>/` (например, `https://93.77.189.231/`)[cite: 4, 6].
*   **Протокол:** HTTPS (Защищенное соединение, порт 443)[cite: 2, 4].
*   **Механика работы:** При открытии страницы отображается динамический сайт, который генерируется каждые 3 секунды. Он показывает реальную нагрузку на процессор (CPU), использование оперативной памяти (RAM) и время работы (Uptime) конкретного сервера[cite: 14]. При обновлении страницы (клавишей F5) имя хоста (например, `web-node-0` на `web-node-1`) меняется, что наглядно доказывает работу балансировщика нагрузки[cite: 14].

### 📊 2. Система мониторинга (Grafana)
*   **Адрес:** `http://<IP_сервера_Grafana>:3000`[cite: 4].
*   **Доступ:** Логин `admin`, Пароль `BobkovDevOps2026` (Пароль безопасно хранится в файле `secrets.yml`, а не в открытом коде)[cite: 10, 13].
*   **Описание:** Инструмент для визуализации потребления ресурсов (процессоров, памяти, дисков). Дашборды импортируются туда автоматически при развертывании[cite: 10].

### 🔍 3. Система аналитики логов (Kibana)
*   **Адрес:** `http://<IP_сервера_Kibana>:5601`[cite: 4].
*   **Описание:** Единая точка для просмотра текстовых логов (журналов событий) со всех серверов и Docker-контейнеров[cite: 11, 14]. Поиск осуществляется через меню **Discover** по индексу `filebeat-*`[cite: 14].

## 1. Архитектура сети и Безопасность (Файл `network.tf`)

Сеть проекта построена по корпоративному стандарту **Zero Trust (Нулевое доверие)**. Это означает, что серверы с критичными данными спрятаны от интернета[cite: 3].

### 1.1. Топология подсетей
Внутри единой виртуальной сети `enterprise-main-vpc` создано 4 подсети, разделенные по двум зонам доступности Яндекса (`ru-central1-a` и `ru-central1-b`)[cite: 3]:
*   **Публичная зона (DMZ):** Подсети `public_a` и `public_b`[cite: 3]. Здесь находятся балансировщик, сервер мониторинга (Grafana), сервер логов (Kibana) и **Bastion Host** (Бастион)[cite: 3, 8]. У этих ресурсов есть "белые" (публичные) IP-адреса.
*   **Приватная зона (Изолированная):** Подсети `private_a` и `private_b`[cite: 3]. Здесь находятся серверы с сайтом (Web Nodes) и хранилище баз данных (Elasticsearch + PostgreSQL)[cite: 3, 8]. У них НЕТ публичных IP-адресов. Подключиться к ним из интернета невозможно.
*   **NAT Gateway:** Чтобы изолированные серверы могли скачивать обновления и программы из интернета, настроен виртуальный роутер `yandex_vpc_gateway`. Он выпускает трафик наружу, но не пускает никого внутрь[cite: 3].

### 1.2. Межсетевые экраны (Security Groups)
Фаерволы жестко контролируют, кто и куда может передавать данные:
*   `bastion_sg`: Разрешает входящий трафик только по порту 22 (SSH) со всего интернета[cite: 3]. Бастион — это единственная входная дверь для администратора.
*   `internal_mgmt_sg`: Защищает базы данных. Порты 9200 (Elastic) и 5432 (Postgres) доступны только внутренним IP-адресам серверов (`10.100.0.0/16`)[cite: 3].
*   `web_sg`: Защищает веб-серверы. Разрешает принимать трафик на порт 80 ТОЛЬКО от группы балансировщика `alb_sg`[cite: 3].

## 2. Вычислительные мощности и Автомасштабирование (Файлы `vms.tf` и `alb.tf`)

Все серверы работают на базе операционной системы **Debian 12**[cite: 8].

### 2.1. Оптимизация бюджета
Чтобы не тратить лишние средства, для сервисных узлов (Бастион, Grafana, Kibana, БД) используется параметр `core_fraction = 20`[cite: 8]. Это означает, что Яндексом гарантируется лишь 20% мощности процессора, чего достаточно для фоновых задач[cite: 8].
Для серверов с сайтом, которые должны быстро отвечать пользователям, выделено 100% мощности процессора (`core_fraction = 100`)[cite: 8].

### 2.2. Балансировка и Автомасштабирование
*   **Application Load Balancer (ALB):** L7-балансировщик принимает запросы пользователей[cite: 2]. На нем настроен **SSL Termination** — балансировщик сам расшифровывает HTTPS-трафик с помощью сертификата `enterprise-alb-ssl-cert-v2` и передает его на серверы в чистом виде по HTTP (порт 80)[cite: 2]. Это экономит ресурсы веб-серверов. Каждые 3 секунды балансировщик проверяет, жив ли сервер (Health Check)[cite: 2].
*   **Instance Group:** Веб-серверы объединены в группу `yandex_compute_instance_group`[cite: 8]. Если нагрузка на процессоры серверов превышает 70% (`cpu_utilization_target = 70`), Яндекс автоматически создает новые машины-клоны (до 3 штук), чтобы сайт не "упал" от наплыва посетителей[cite: 8].

### 2.3. Абсолютная автоматизация (Ресурс null_resource)
В конце файла `vms.tf` находится специальный блок `null_resource.run_ansible`. Он настроен через жесткую зависимость (`depends_on`) от всех виртуальных машин[cite: 8]. Как только Terraform заканчивает создание инфраструктуры, этот блок дает команду локальному компьютеру: `bash run_ansible.sh`[cite: 8]. Благодаря этому Ansible запускается абсолютно автоматически, без участия человека.

## 3. Настройка серверов и Баз Данных (Скрипты Ansible)

### 3.1. Базовая настройка и Логирование (`playbook_logging.yml`)
*   **Зеркала и Docker:** Чтобы скачивание пакетов не обрывалось по таймауту, Ansible перенастраивает серверы на быстрые зеркала Яндекса (`mirror.yandex.ru`) и устанавливает Docker[cite: 12].
*   **Ядро ОС:** Для запуска поискового движка Elasticsearch скрипт принудительно увеличивает лимит памяти ядра Linux (`vm.max_map_count = 262144`)[cite: 12].

### 3.2. Реляционная СУБД и pg-adapter (`deploy_infra_logging.yml`)
Это ключевой этап настройки персистентного хранения метрик, исключающий потерю данных при перезапуске прерывистых (Preemptible) виртуальных машин Яндекса.
*   **PostgreSQL:** Разворачивается надежный контейнер реляционной базы данных `postgres:15-alpine` в режиме `network_mode: host`[cite: 11]. Для обеспечения безопасности директории с данными (`/opt/postgres/data`) жестко назначаются права `0750`[cite: 11].
*   **CrunchyData Go-адаптер (pg-adapter):** Рядом с базой разворачивается специализированный контейнер-экспортер `postgres-exporter:v0.15.0`[cite: 11]. Он подключается к ядру PostgreSQL через скрытую строку подключения `DATA_SOURCE_NAME` (пароль `crunchy_admin` берется из `secrets.yml`)[cite: 11, 13].
*   **Роль pg-adapter:** Этот компонент работает как мост. Он транслирует данные и метрики из реляционной СУБД в формат, который понимает Prometheus, гарантируя сохранность исторической телеметрии кластера[cite: 11].

### 3.3. Динамический Web-сайт и Filebeat (`update_web.yml`)
*   **Сайт-заглушка:** Создается Bash-скрипт, который регистрируется как системная служба Linux (`dynamic-website.service` в Systemd)[cite: 14]. Служба каждые 3 секунды опрашивает ядро ОС (узнает CPU, RAM) и переписывает файл `index.html`[cite: 14].
*   **Сбор логов (Docker Metadata):** Устанавливается агент Filebeat[cite: 14]. Для него настроен процессор `add_docker_metadata` (проброс `/var/run/docker.sock`)[cite: 14]. Filebeat собирает логи из контейнеров (`/var/lib/docker/containers/*/*.log`) и автоматически дописывает к каждой строчке лога системное имя контейнера[cite: 14].

## 4. Мониторинг и Service Discovery (`deploy_grafana.yml`)

Мониторинг инфраструктуры организован по Pull-модели с продвинутыми механизмами автоматизации.
*   **Динамический Service Discovery (Поиск целей):** Так как веб-серверы создаются динамически, мы не можем вписать их IP-адреса руками. Ansible с помощью циклов (Jinja2) генерирует конфигурации `targets_nginx.json` и `targets_postgres.json`[cite: 10]. Prometheus автоматически считывает из них актуальные IP-адреса серверов и адаптера `pg-adapter` (порт 9187)[cite: 10, 11].
*   **Автоимпорт дашбордов:** Ansible через модуль `get_url` скачивает официальные графики Grafana (ID 1860 для серверов, ID 12708 для Nginx)[cite: 10]. Затем утилитой `sed` автоматически подставляется нужное имя источника данных, и файлы импортируются в Grafana через Provisioning[cite: 10].

## 5. Резервное копирование (Backup)

Для защиты данных от сбоев в дата-центрах Яндекса, в `vms.tf` настроено облачное расписание (`yandex_compute_snapshot_schedule`)[cite: 8]. 
Каждую ночь в 02:00 UTC система создает резервную копию (снимок) дисков Бастиона, Grafana, Kibana и сервера баз данных (Elastic + PostgreSQL)[cite: 8]. Снимки хранятся ровно 7 дней (`snapshot_count = 7`), после чего старые архивы циклично перезаписываются новыми[cite: 8].

## 6. Решение архитектурных проблем (Troubleshooting)

В ходе разработки проекта мы столкнулись с рядом сложных инженерных задач и успешно их решили.

**Проблема 1: Балансировщик блокировал доступ к сайту (Health Checks Failing).**
*   *Симптомы:* Сайт недоступен, балансировщик помечает бэкенды красным статусом "Unhealthy".
*   *Причина:* В фаерволе (`alb_sg`) был разрешен только один статический порт `30080` для подсетей проверок Яндекса (`198.18.235.0/24`)[cite: 3].
*   *Решение:* Служебные узлы Яндекса используют множество динамических портов. Мы расширили правило в `network.tf`, разрешив диапазон портов `from_port = 1, to_port = 65535` для служебных подсетей[cite: 3].

**Проблема 2: Ошибка аутентификации Ansible (Конфликт ProxyJump).**
*   *Симптомы:* Ansible выдавал `Permission denied (publickey)` при попытке настроить серверы в приватной сети.
*   *Причина:* При маршрутизации через Бастион жестко указанный путь к ключу в инвентарном файле заставлял SSH использовать этот ключ только для конечного сервера[cite: 8].
*   *Решение:* Использование механизма `ssh-agent`. Скрипт `run_ansible.sh` загружает сгенерированный приватный ключ в оперативную память агента, что обеспечивает прозрачную авторизацию по всей цепочке подключения[cite: 5].

**Проблема 3: Блокировка панелей мониторинга провайдером.**
*   *Симптомы:* В браузере не открывались Kibana (порт 5601) и Grafana (порт 3000), хотя настройки безопасности в Яндексе были верными[cite: 3, 4].
*   *Причина:* Многие домашние провайдеры и корпоративные брандмауэры блокируют нестандартные порты.
*   *Решение:* Использование технологии локального туннелирования **SSH Port Forwarding**. Трафик панелей прокидывается внутри зашифрованного туннеля поверх стандартного порта 22: `ssh -N -L 5601:<Внутренний_IP>:5601 debian@<IP_Бастиона>`. После этого сервисы безопасно доступны локально.
